Strict budget caps (enforcement protocol v4). `CloudAdapter` now polls rules with `X-Traice-Enforcement-Version: 4` and receives `strictCaps`: the strictly capped budgets past 90% of their limit that apply to this API key. Before each call one of them applies to, right before the provider call and after rate limits, the SDK asks trAIce to check the call (`POST /api/v1/budget-caps/acquire`) with the model the call goes to, the provider, feature, user, a rough input token count, and the request's output token limit, never the request text. Cache hits make no check. A refusal throws `TraiceEnforcementError` with action `DENY`, the cap's rule, and `reason.strictCap: true`, without calling the provider, and is reported as a blocking decision. The SDK waits at most the advertised `timeoutMs` (300 ms); if trAIce does not answer, it lets the call through unless a matching active cap says `onUnavailable: "block"`. Caps in preview never block. An allowed call's reservation ids go back with the next event of the same model and feature (`capReservationIds`), so trAIce releases its estimate once the real cost is recorded. A strict cap refusal is never retried by a fallback rule or a rollout's source fallback. `matchStrictCaps()` matches the caps, with conformance cases in `strict-cap-v1.json`, and `getStrictCapStats()` reports checked, refused, unavailable, blocked-while-unavailable, and preview counts.
